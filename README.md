## Run locally

Use JDK 17, Maven and PostgreSQL. Create a database owned by the application role. For example, as a PostgreSQL administrator:

```sql
CREATE ROLE app LOGIN PASSWORD 'replace-with-a-local-password';
CREATE DATABASE smartcity OWNER app;
```

From the project root:

    export DATABASE_URL=jdbc:postgresql://localhost:5432/smartcity
    export DB_USER=app
    export DB_PASSWORD='replace-with-a-local-password'
    export CV_STORAGE_DIR="$HOME/.smartcity/cvs"
    mvn spring-boot:run

Open http://localhost:8080/ and register through **Account**. A student account can upload PDF CVs and apply for jobs. Use a writable upload directory outside the app's static files. Back it up alongside PostgreSQL.

A new PostgreSQL database starts without directory records or accounts. To give your first account Admin access, run this SQL as the database operator with the username you registered. Sign in again and open **Administration** to enter cities and listings.

    WITH chosen AS (
        SELECT id FROM userses
        WHERE username = 'your-registered-email@example.com'
          AND password_hash IS NOT NULL AND admin_id IS NULL
    ), granted AS (
        INSERT INTO admins(adminid, authorization_level)
        SELECT id, 1 FROM chosen RETURNING id, adminid
    )
    UPDATE userses u SET admin_id = granted.id
    FROM granted WHERE u.id = granted.adminid;

Set **APP_ANALYTICS_COLLECTION_ENABLED=true** to count future opted-in visits. Analytics starts empty and uses page identifiers and timestamps. The current collector does not derive locations.

### Registration returns 404 or saving your profile returns 405

A Spring Boot process started before an account route was added can serve the updated frontend while still returning 404 for registration or 405 for profile and password updates. Stop the old process from the terminal where it is running, restart it from the current source with the same database settings, and reload the page. Use the Spring Boot URL when registering.

### Upgrade an existing Hibernate-managed database

Back up the database. Restore a copy into a separate test database and compare its structure to [the V1 baseline](src/main/resources/db/migration/V1__legacy_schema.sql). For a compatible schema without Flyway history, start once with `DB_BASELINE_ON_MIGRATE=true` and the database connection settings above. Flyway records version 1 as the baseline and applies version 2 onward. Remove the flag after startup. On a fresh database the flag is unnecessary.

The migrations preserve existing user data and remove tagged synthetic visits and recognizable, unlinked catalogue fixtures. Review any old demo accounts and records that have been edited or referenced by other rows before deciding whether to remove them. The upgrade leaves those records intact and retires the shared demo sign-in.

### Tests

```bash
mvn test
```

The default suite uses H2 for existing API tests. To also run Flyway, persisted CRUD, concurrency, CV/application and news checks, create a **separate disposable PostgreSQL database** owned by the test role. The tests create a unique schema in that database on each run.

```bash
export SMARTCITY_TEST_DATABASE_URL=jdbc:postgresql://localhost:5432/smartcity_test
export SMARTCITY_TEST_DB_USER=app
export SMARTCITY_TEST_DB_PASSWORD='replace-with-the-test-password'
mvn test
```

Integration fixtures load only from the test classpath. Run the preference and navigation logic checks with Node.js 24:

```bash
node --test src/test/frontend/cookie-preview.test.mjs
```

See [the frontend guide](FRONTEND.md) for the cookie controls, demo analytics, and current security boundaries.
